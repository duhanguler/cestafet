# cestafet v0.2 — Design

Status: draft · 2026-11-22 · builds on [design.md](design.md)

v0.1 delivers a notice once, at the recipient's next prompt or tool call. v0.2 makes the main use
case — *"testing has started, do not deploy to staging"* — complete: such a notice stays in force
until it is lifted, reaches sessions that sit idle, and can warn before the forbidden command runs.

## 1. Standing rules and lifting

### Problem

"Do not deploy to staging" is not news, it is a rule with a lifetime. Today it is a one-off
notice: a session that starts 25 hours later never hears it (backfill window 24 h), a session that
heard it may forget it after compaction, and "testing finished, deploys allowed" is just another
notice with no link to the first.

### Model

A notice gets a kind:

| kind | meaning | delivered to |
|---|---|---|
| `info` | news (current behaviour) | live sessions; new sessions within 24 h |
| `rule` | stays in force until lifted or expired | live sessions; **every** new session while active |

New columns on `notices`: `kind` (`info` default), `expires_at` (nullable), `lifted_at`,
`lifted_by_session`, `lifted_by_notice`. A rule is *active* when not lifted and not expired.

### Tools

- `notify` gains `standing: bool` and `expires_in` (e.g. `"2h"`, `"1d"`, max 30 d). The skill
  maps phrasing like "until …", "from now on", "no deploys while testing" to `standing: true`.
- New `lift(notice_id, body?)`: marks the rule lifted and sends an `info` notice
  ("Lifted: …") that references it. The skill maps "testing finished, deploys are allowed again"
  to `lift` of the matching active rule (it calls `rules` first to find it).
- New `rules()`: active rules of the project with sender, origin, age and expiry.

### Delivery

- `SessionStart` orientation lists every active rule of the project (compact form, max 10, newest
  first), in addition to pending notices. This also restores rules after `/compact`
  (`source: "compact"`).
- Backfill: active rules regardless of age; `info` notices keep the 24 h window.
- Lifting a rule delivers the lift notice to the sessions that received the rule.

### Tests

Store: expiry and lifting state; backfill selects active rules of any age and recent info only;
lifting twice fails; lifting another project's rule fails. Hooks: orientation lists active rules
and omits lifted/expired ones; compact re-lists them.

## 2. Push delivery to idle sessions (channels)

### Problem

A session waiting for its user never fires a hook, so a notice waits until the user returns.

### What Claude Code offers (inspected in 2.1.330)

- An MCP server can declare the experimental capability `claude/channel` and send
  `notifications/claude/channel`; Claude Code then injects the content into the session.
- A channel is only active when the session is started with `--channels <servers…>`, and the
  server must be on Anthropic's approved channel allowlist. Otherwise the session needs
  `--dangerously-load-development-channels <servers…>` or an organisation allowlist
  (`allowedChannelPlugins` in managed settings).

So push delivery is **opt-in** and, until cestafet is allowlisted, needs the development flag.

### Design

- The MCP server declares `claude/channel`, resolves its session as today and polls the store
  every 2 s for that session's undelivered notices (a single indexed query; SQLite in WAL mode).
- When a channel notification is sent, the delivery gets `pushed_at`. The hooks treat a pushed
  notice as delivered **only** if the session has confirmed channel delivery (see spike), so a
  session without channels still gets it from the hook and never twice.
- `cestafet setup` prints the opt-in launch line per profile (e.g. an alias adding the flag); it
  never edits shell files.

### Spike before implementation

1. Exact notification payload and how Claude Code renders it; whether it reaches a session that
   is idle at the prompt and a session in the middle of a turn.
2. How the MCP server can tell that its channel is active (capability negotiation, a client
   response, or a confirmation the model sends through a tool) — this decides deduplication.
3. Behaviour without `--channels`: dropped silently, error, or queued.
4. What submitting cestafet for the channel allowlist requires.

If (2) has no reliable answer, the fallback is: push as a *nudge* only ("1 new cestafet notice —
it will be shown at your next step"), keep the hook as the single delivery path.

## 3. Guard hook (optional)

### Problem

An informed session can still run the forbidden command — after compaction, from a subagent, or
when the model misjudges.

### Design

- A rule may carry `guard` patterns: up to 5 glob patterns, each ≤ 120 chars, matched
  case-insensitively against Bash commands (e.g. `*deploy* staging*`, `kubectl * -n staging *`).
  The sending model derives them from the user's words; the skill asks it to keep them narrow.
- A `PreToolUse` hook (matcher `Bash`) checks the command against the guards of the project's
  active rules. On a match it returns `permissionDecision: "ask"` with the reason
  ("cestafet rule #12 from the coordinator: Testing has started. Do not deploy to staging.").
  The user decides; cestafet never silently denies.
- Cost: one indexed query per Bash call, skipped entirely when the project has no guarded rule.
- Subagent calls are guarded too (unlike notice injection, a guard is not consumed).

### Tests

Pattern validation; match/no-match table; lifted and expired rules do not guard; other projects'
rules do not guard; the hook output shape.

## Out of scope for v0.2

Codex adapter, cross-machine delivery, encryption, per-notice access control.
