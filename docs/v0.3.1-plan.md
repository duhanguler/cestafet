# v0.3.1 — Claude desktop app on Windows

## Source

A user running Claude Code only from the Claude desktop app on Windows 11 (an MSIX package with
its own `claude.exe`, nothing on PATH) reported seven suggestions after their first day on 0.3.0.
The plan below was refereed on 2026-11-23 (tiers 0-3: MiMo V2.6 Flash, Muse Wonder, GPT-6.2 Astra,
Fable 5.2); all four returned APPROVE_WITH_CHANGES and their required changes are folded in.

## Findings (verified in code at c98c8c3)

1. `setup` and `doctor` run `claude` from PATH only (`internal/setup/install.go:28`).
2. After install, the desktop app must be fully quit from the tray; it reads PATH only at start.
3. Windows data defaults live under `%LOCALAPPDATA%` / `%APPDATA%`. MSIX redirects new files that
   packaged processes create there to `Packages\<family>\LocalCache\...`, so desktop-app sessions
   and terminal/VS Code processes see different databases. Existing files are modified in place,
   so a database created outside the package can get its `-wal`/`-shm` redirected (unverified,
   plausible).
4. Changing the data location loses the coordinator role and rules unless they are migrated.
5. After an app restart, old sessions reappear only after a message (Claude Code behaviour).
6. `paths.Canon` does not expand 8.3 short names.
7. Identity needs a `claude.exe` ancestor; an npm launch through `node.exe` is not recognised.

## Decisions

### 1. Data location (Windows only)

- Default: `%USERPROFILE%\.cestafet\bus.db`, `%USERPROFILE%\.cestafet\projects.toml`, and the hook
  error log `%USERPROFILE%\.cestafet\hook-errors.log` (out of `os.UserCacheDir`, also virtualized).
- `CESTAFET_DB`, `CESTAFET_PROJECTS` and XDG variables keep precedence; when one selects a path,
  no migration happens for that file. darwin/linux are unchanged.

### 2. Migration (Windows only, built-in default only)

- Runs **before** `store.Open` creates anything, for the database and `projects.toml`
  independently.
- Candidates: the real `%LOCALAPPDATA%\cestafet` / `%APPDATA%\cestafet`, and every
  `%USERPROFILE%\AppData\Local\Packages\*\LocalCache\{Local,Roaming}\cestafet` found by glob (no
  hard-coded package family; never derived from `%LOCALAPPDATA%`, whose view depends on the
  caller's package context).
- Precedence is deterministic, the same whichever process migrates: the candidate with the newest
  activity (latest session/notice timestamp in the database, file mtime for `projects.toml`);
  empty databases lose. `cestafet migrate --from <path>` overrides the choice. No merging.
- Single winner: an exclusive lock file in `.cestafet` is taken before the "no database" check;
  the database is copied with `VACUUM INTO` to a temporary file in the target directory, checked
  with `PRAGMA integrity_check`, then published with a no-replace move. Stray `-wal` files away
  from their main file are reported, not silently ignored. An interrupted migration is retried on
  the next open.
- A failed migration never fails a hook: start empty, log, and let `doctor` report it.
- Old files stay in place. `doctor` lists them; a candidate written after the migration time is
  reported as **active** (a 0.3.0 process is still writing), otherwise as stale.

### 3. Finding `claude.exe` (setup, uninstall, doctor share one resolver)

Order: `claude` on PATH; else the nearest verified Claude Code ancestor's full image path
(`QueryFullProcessImageNameW`); else the newest
`%LOCALAPPDATA%\Claude-Data\*\claude-code\<version>\*\claude.exe` by numeric version. Reject paths
under `\WindowsApps\` (the desktop app's own `claude.exe`) and check `--version` before use. The
chosen path is printed.

### 4. 8.3 short names

A Windows-only wrapper calls `GetLongPathNameW` on existing paths (strip `\\?\`, fall back to the
input on error) before the pure `canon`; `Canon`, `Same` and `Within` all go through it. Fix
`tilde`'s raw `p[len(home):]` slice for spellings of different length. Changelog note: path-keyed
projects stored under a short spelling need re-adding.

### 5. README (Windows section)

- Desktop app: after install, Quit it from the tray and start it again; "Connection closed" from
  the MCP server usually means `cestafet.exe` is not on the app's PATH.
- Upgrading from 0.3.0: quit the app and all sessions first, so no old process keeps writing the
  old database.
- After an app restart, earlier sessions reappear once they get a message.
- `CESTAFET_DB` / `CESTAFET_PROJECTS` documented.
- Identity needs Claude Code's native `claude.exe` in the process chain.

## Release gate (Windows VM, before tagging)

- Desktop app: two sessions plus a terminal `cestafet sessions`, notify/ack.
- 0.3.0 → 0.3.1 upgrade of a terminal-only database with a standing rule and an uncheckpointed
  WAL: the rule survives.
- Both real and package copies present: the newer one wins, `doctor` lists the other.
- Two sessions starting at the same time on first run: one migration, no empty winner.
- A project under a real 8.3 path matches its long spelling.

## Known limits

- Downgrading to 0.3.0 returns to the old database; there is no merge back.
- Virtualization depends on the app's manifest and may change with app updates.
