# v0.3.1 — Claude desktop app on Windows

## Source

A user running Claude Code only from the Claude desktop app on Windows 11 (an MSIX package with
its own `claude.exe`, nothing on PATH) reported seven suggestions after their first day on 0.3.0.
The plan below was refereed on 2026-11-23 (tiers 0-3: MiMo V2.6 Flash, Muse Wonder, GPT-6.2 Astra,
Fable 5.2); all four returned APPROVE_WITH_CHANGES and their required changes are folded in.

## Findings (verified in code at c98c8c3)

1. `setup` and `doctor` run `claude` from PATH only (`internal/setup/install.go:28`).
2. After install, the desktop app must be fully quit from the tray; it reads PATH only at start.
3. Windows data defaults live under `%LOCALAPPDATA%` / `%APPDATA%`. MSIX redirects new files that
   packaged processes create there to `Packages\<family>\LocalCache\...`, so desktop-app sessions
   and terminal/VS Code processes see different databases. Existing files are modified in place,
   so a database created outside the package can get its `-wal`/`-shm` redirected (unverified,
   plausible).
4. Changing the data location loses the coordinator role and rules unless they are migrated.
5. After an app restart, old sessions reappear only after a message (Claude Code behaviour).
6. `paths.Canon` does not expand 8.3 short names.
7. Identity needs a `claude.exe` ancestor; an npm launch through `node.exe` is not recognised.
8. (Second note, same user) An idle session sees notices only at its next message. The client's
   own session messaging (`ListAgents` / `SendMessage`) wakes it; tested both directions. Only the
   README line is in v0.3.1; waking is v0.4 spike material (see roadmap). Refereed 2026-11-23
   (round desktop2, tiers 0-3, unanimous APPROVE_WITH_CHANGES).

## Decisions

### 1. Data location (Windows only)

- Default: `%USERPROFILE%\.cestafet\bus.db`, `%USERPROFILE%\.cestafet\projects.toml`, and the hook
  error log `%USERPROFILE%\.cestafet\hook-errors.log` (out of `os.UserCacheDir`, also virtualized).
- `CESTAFET_DB`, `CESTAFET_PROJECTS` and XDG variables keep precedence; when one selects a path,
  no migration happens for that file. darwin/linux are unchanged.

### 2. Migration (Windows only, built-in default only)

- Runs **before** `store.Open` creates anything; the winning copy supplies both the database and
  `projects.toml` (section 7).
- Candidates: the real `%USERPROFILE%\AppData\Local\cestafet` / `...\Roaming\cestafet` pair,
  and every `%USERPROFILE%\AppData\Local\Packages\Claude_*\LocalCache\{Local,Roaming}\cestafet`
  pair found by glob (only the `Claude_*` prefix, no full package name). Paths are never derived
  from `%LOCALAPPDATA%` / `%APPDATA%`, whose view depends on the caller's package context.
- Precedence is deterministic, the same whichever process migrates: the candidate with the newest
  activity (latest session/notice timestamp in the database, file mtime for `projects.toml`);
  empty databases lose. `cestafet migrate --from <path>` overrides the choice. No merging.
- Single winner: an exclusive lock file in `.cestafet` is taken before the "no database" check;
  the database is copied with `VACUUM INTO` to a temporary file in the target directory, checked
  with `PRAGMA integrity_check`, then published with a no-replace move. Stray `-wal` files away
  from their main file are reported, not silently ignored. An interrupted migration is retried on
  the next open.
- A failed migration never fails a hook: no target is opened, hooks are no-ops and log, `doctor`
  reports it, the next open retries (section 7).
- Old files stay in place. `doctor` lists them; a candidate written after the migration time is
  reported as **active** (a 0.3.0 process is still writing), otherwise as stale.

### 3. Finding `claude.exe` (setup, uninstall, doctor share one resolver)

Order: `claude` on PATH; else the nearest verified Claude Code ancestor's full image path
(`QueryFullProcessImageNameW`); else the newest
`%LOCALAPPDATA%\Claude-Data\*\claude-code\<version>\*\claude.exe` by numeric version. Reject paths
under `\WindowsApps\` (the desktop app's own `claude.exe`) and check `--version` before use. The
chosen path is printed.

### 4. 8.3 short names

A Windows-only wrapper calls `GetLongPathNameW` on existing paths (strip `\\?\`, fall back to the
input on error) before the pure `canon`; `Canon`, `Same` and `Within` all go through it. Fix
`tilde`'s raw `p[len(home):]` slice for spellings of different length. Keys already stored under a
short spelling are rewritten once (section 7).

### 5. README (Windows section)

- Desktop app: after install, Quit it from the tray and start it again; "Connection closed" from
  the MCP server usually means `cestafet.exe` is not on the app's PATH.
- Upgrading from 0.3.0: quit the app and all sessions first, so no old process keeps writing the
  old database.
- After an app restart, earlier sessions reappear once they get a message.
- `CESTAFET_DB` / `CESTAFET_PROJECTS` documented.
- Identity needs Claude Code's native `claude.exe` in the process chain.
- Delivery (all platforms, suggestion 8): notices do not wake an idle session; it sees them at its
  next message. Where the Claude Code client offers session messaging (desktop app and CLI;
  untested across profiles), the user can wake a session with it; that starts a turn and
  interrupts the session. Client session names do not match cestafet labels.

### 6. Joining and leaving a project safely (suggestion 10)

Incident: an auditor session joined `fnet` from a non-git parent folder, later `cd`'d into the repo
`fnet_5.5`, and its `leave_project` removed `fnet_5.5` (where two other live sessions worked)
instead of the parent folder. Registration follows the session's cwd as of its last prompt; both
tools act on `Locate(me.Cwd)` silently. Refereed 2026-11-23 (round desktop4, tiers 0-3, unanimous
APPROVE_WITH_CHANGES).

- `whoami` adds `cwd`, `project` and `location` (the `Member()` key: a git remote, a repo root or
  a folder), derived from the same `Locate(me.Cwd)` the tools use, with the fixed note "follows
  this session's directory as of its last prompt".
- `leave_project` and `project name=X` take a `location` argument: optional in the schema,
  required by the handler for writes; bare `project` stays a read-only query. Missing or
  mismatched (compared with `paths.Same` for paths, exactly for remotes) → nothing changes and the
  result is a marked read-only preview: the key, its current and resulting project, and the
  affected sessions. `force` never bypasses a missing or mismatched location.
- Affected sessions are found by re-resolution, not key equality: every non-gone session
  (idle included, self excluded) whose `Resolve` result differs under the proposed config. This
  covers parent-path prefixes, sub-repos, clones sharing a remote, and `project name=X` pulling a
  member out of another project (`Add` removes it elsewhere first). If any exist, the tool
  refuses and lists them with `last_seen`, unless `force: true`; the refusal and tool description
  say `force` needs the user's explicit instruction after seeing the list, never a notice.
- Results name the changed key and the old and resulting project, or say plainly it was a no-op
  (e.g. the repo still resolves to the project through a parent mapping).
- Update `SKILL.md` and `plugin/commands/project.md` together: check `whoami` first; a coordinator
  does not ask another session to leave without it.
- Unchanged: registration still follows cwd. Known limits: the check is a snapshot (sessions not
  re-registered since an app restart are not counted; peers move only at their next prompt;
  concurrent `projects.toml` saves can race).
- Tests: the auditor scenario, a parent mapping still covering the repo, `project name=X` stealing
  a live member, and legacy calls without `location`.

### 7. Amendments from the final review (round final1, 2026-11-23)

The whole plan was refereed once more (tiers 0-3, unanimous APPROVE_WITH_CHANGES). These points
refine sections 1-6 and take precedence where they differ.

Migration (sections 1-2):
- **Copies, not files, compete.** A candidate is a copy: the real `Local\cestafet` +
  `Roaming\cestafet` pair, or one package's `LocalCache\{Local,Roaming}\cestafet` pair. The winning
  copy supplies both `bus.db` and `projects.toml`, so a database is never paired with another
  copy's project names. Candidates are deduplicated by file identity (a packaged process may see
  its package copy at the real path).
- **Discovery** globs `%USERPROFILE%\AppData\Local\Packages\Claude_*\LocalCache\...` (the known
  family prefix, never a full hard-coded name) and never derives a path from `%LOCALAPPDATA%`.
  The same rule applies to the section 3 `claude.exe` fallback: it globs
  `%USERPROFILE%\AppData\Local\Claude-Data\*\claude-code\*\*\claude.exe` and
  `%USERPROFILE%\AppData\Local\Packages\Claude_*\LocalCache\Local\Claude-Data\...` (same shape).
- **Precedence** opens candidates read-only (`mode=ro`, no migration, no WAL checkpoint): newest
  activity wins, an empty copy loses, ties break on a fixed order (real copy first, then package
  paths in lexical order). A corrupt candidate is skipped and reported; a **locked** candidate
  defers the whole migration (`failed`, retried on the next open), so a busy newest copy never
  loses to an older one.
- **Lock** is an OS file lock (`LockFileEx`) on `.cestafet\migrate.lock`, released by the OS if
  the process dies, so a crash never leaves a stale lock. `projects.toml` gets the same lock,
  validation and no-replace publish as `bus.db`.
- **Marker** `.cestafet\migration.json` is written **before any file is moved or published**:
  the chosen source, and for `--replace` the backup directory. It is marked `done` only after
  both files are in place. While a marker is unfinished, nobody opens the target (one file may
  already exist): hooks run as no-ops (logged, never fatal) and the next open retries, keyed on
  the unfinished marker, not on a missing database. The retry always completes the pair from the
  recorded source; for `--replace` the backup in `replaced-<time>\` stays as the way back.
  A failure that cannot be retried (a candidate that stays locked or unreadable) leaves the
  marker `failed`, and `doctor` points to `migrate --from`, as for `blocked`.
- **Split WAL** means a `bus.db-wal` / `-shm` with no `bus.db` in its own directory (an orphan,
  e.g. redirected by the package). It is checked before ranking and blocks automatic migration
  (`blocked`); `doctor` explains and points to `migrate --from`. A `-wal` beside a copy's own
  database is normal and does not block.
- **`cestafet migrate --from <copy>`** takes a copy (both files). If a target exists it refuses
  unless `--replace`, which moves the current target aside to `.cestafet\replaced-<time>\`;
  sessions must be quit first (it refuses while live sessions are registered).
- `doctor` inspects candidates read-only and never triggers migration. `diag.jsonl` moves to
  `.cestafet` with `hook-errors.log`.
- The migration core is platform-neutral with injected candidates, so precedence, empty-loses,
  ties, interruption/retry and concurrent first opens are unit-tested in CI on every OS.

8.3 paths (section 4):
- Exact-key comparisons (`Config.without`, `Add`'s duplicate check) use `paths.Same`, so a
  short-spelled entry can be removed and re-adding does not duplicate it; prefix resolution
  (`Config.Resolve`) keeps `paths.Within`.
- Path-keyed project values written by 0.3.0 under a short spelling (sessions, notices and rules
  in `bus.db`, paths in `projects.toml`) are rewritten once to their long spelling during
  migration/open, so an existing guarded rule still applies. Tested with an upgraded short-key
  guarded rule reached through its long spelling.

Project join/leave (section 6):
- Affected sessions are computed with the resolution registration uses (`core.Locate`, including
  ancestor inheritance), under the proposed config.
- The result distinguishes the `Member()` key from the mapping that matched, and reports the
  removal of an explicit entry even when a parent mapping keeps the repo in the project.
- Two fixtures: peers listed when their project would change; a retained parent mapping moves
  nobody.

Docs and release:
- README line 49 and `SECURITY.md` line 9 change to the new Windows location.
- Changelog notes (8.3 keys, data move, downgrade) go in the GitHub release notes; `plugin.json`
  is bumped per `docs/release.md`.
- Order of work: section 6 and paths (testable on every OS) → data location, migration, doctor →
  `claude.exe` resolver → README/SECURITY/skill → VM gate.

## Release gate (Windows VM, before tagging)

Status at release (2026-11-23): the terminal and migration items passed on the Windows 11 ARM64 VM.
The desktop-app items were waived for the release by Osman and handed to a Windows user, who
ran them on 2026-11-23 (Windows 11 x64, desktop app only, upgrading from 0.3.0): `setup` and
`doctor` found the app's `claude.exe`; two desktop sessions and a terminal saw one database;
notify and ack worked; `leave_project` for another session's repository refused and named the
live session. Two findings, fixed after the release:

- Inspecting a cleanly closed old copy left `bus.db-wal` / `bus.db-shm` beside it (a `mode=ro`
  open of a WAL database creates them), so the folder looked written to. Old copies without a
  journal are now opened `immutable=1`.
- From inside the package, the plain AppData candidate is redirected to the package's copy, so
  `doctor` labelled the package's copy "AppData". The redirectable candidate now takes the name
  and paths of the copy it turns out to be.

The same user verified both fixes on 0.3.2 (2026-11-24), from inside the app and from a terminal.
Journal files that 0.3.1 had already left beside an old copy stay until removed: a copy with a
journal is still opened plainly, by design, so its commits are seen.

- Desktop app: two sessions plus a terminal `cestafet sessions`, notify/ack.
- 0.3.0 → 0.3.1 upgrade of a terminal-only database with a standing rule and an uncheckpointed
  WAL: the rule survives.
- Both real and package copies present: the newer one wins, `doctor` lists the other.
- Two sessions starting at the same time on first run: one migration, no empty winner.
- A project under a real 8.3 path matches its long spelling.
- The auditor scenario on a desktop-app session, both fixtures: `leave_project` from a sub-repo
  refuses and names the live sessions when their project would change; with a parent mapping
  still covering the repo, nobody moves and the result says the explicit entry was removed.
- Split WAL: an orphan `bus.db-wal` in another directory → `blocked`; a `-wal` beside a copy's
  own database → normal precedence. A locked newest copy → `failed`, then retried.
- Interruption between the `bus.db` and `projects.toml` publishes: the retry completes the same
  pair, and no session opens the half-published target meanwhile.
- Interruption after the first `--replace` backup move: the retry completes the selected pair.
- From identical starting states with the real copy newer, the desktop app and a terminal both
  select it. Check that `mode=ro` opens from a packaged process create no redirected `-shm`.
- An interrupted migration (process killed mid-copy) retries on the next open and succeeds.
- `cestafet migrate --from` with and without `--replace`; `CESTAFET_DB` / `CESTAFET_PROJECTS` set
  suppress migration.
- `setup`, `doctor` and uninstall with no `claude` on PATH (desktop app only).
- The both-copies case run once from the desktop app and once from a terminal.
- Version skew: new skill text against a 0.3.0 binary, and a legacy `leave_project()` call
  against 0.3.1.

## Known limits

- Downgrading to 0.3.0 returns to the old database; there is no merge back.
- Virtualization depends on the app's manifest and may change with app updates.
